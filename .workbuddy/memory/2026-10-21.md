## OpenRadio 项目启动：设计路线定稿

项目：Minecraft 1.21.1 NeoForge 硬核无线电通信 Mod（modid `openradio`，包 `com.rinko.openradio`）。
README.md 是初步技术草案 v0.1（简化仿真 + 效果模拟 + 服务端权威 + 异步计算）。

### 已定架构决策（用户确认）

1. **砍掉异步计算层**，改为主线程 tick 时间预算制（默认 ~2ms/tick，超预算顺延）。
   理由：快照阶段本身需读 World + DDA 射线，只能主线程，是 95% 开销；异步只剩浮点算术，
   收益≈0 却要背崩档/时序/可见性风险。
2. **砍掉全局持久化设备注册表**。设备状态跟随自身：手持机 = ItemStack DataComponent，
   固定台 = BlockEntity。服务端只维护内存索引（维度+频率 → 设备引用），随区块加载卸载增删，不落盘。
3. **SVC（Simple Voice Chat）降级为 M5 之后的可选软依赖**。先做完整的数据/文本模式
   （硬核无线电核心玩法），语音后置。
4. **跨维度默认不通**，不做维度间衰减系数。
5. **通信模型 = 频道广播式**：一个频率 = 一个频道，所有同频开机设备互相可见可收。
   不用点对点寻址（避免呼叫/接听状态机）。
6. **M1 首发形态 = 文本/数据模式**，不做语音。
7. 频率用整数表示（建议 1000–99999 虚构单位），配 band 表映射频段。避免浮点精度问题。

### 里程碑（重排，合并原 M0+M1）

## M1 最小闭环（已完成服务端链路 + 客户端面板，待实机验证）

### 用户补充决策

- M1 收信用**聊天栏**，发信用**弹窗面板**；"接收消息列表"推迟到细分电台种类时再做。

### 关键架构：MessageSink 投递抽象

`radio/delivery/MessageSink` 是给语音预留的最关键接缝：

- 发送链路（校验 → 找同频 → 逐个算 Q）完全不关心消息最终形态。
- `ChatMessageSink` 现在读 `text`，按 Q 降级后进聊天栏。
- 将来的 `VoiceSink` 忽略 `text`，只用 `quality` 驱动噪声/低通/断音。
- 降级发生在**投递层而非发送时**，因为同一句话对不同接收者 Q 不同，清晰度也不该一样。
- `RadioManager.setSink()` 可热替换。

### 服务端判定逻辑（RadioManager）

- 不持有设备注册表，每次重算现扫在线玩家手里的开机电台 —— 下线/丢物品/换手自动正确。
- 每个电台的 Q = 与同频设备中**最强**那一个的质量（即"能不能通到人"）。
- Q 变化超 `qSyncThreshold` 才发 S2C，避免刷包。
- 发射只在**同维度**内找接收者；超过 `maxRangeBlocks` 直接静默（连噪声都没有）。
- 反刷屏：`transmitCooldownTicks` 默认 10 tick。
- 所有校验在服务端，客户端只发意图。

### 已解决问题的坑

- `StreamCodec.composite(ByteBufCodecs.X, ...)` 推断出的是 `StreamCodec<ByteBuf, T>`，
  不能声明成 `StreamCodec<FriendlyByteBuf, T>`（ByteBuf 是父类型）。必须用 `io.netty.buffer.ByteBuf`。
- 事件总线不用 `@EventBusSubscriber` 自动分派，一律显式 `addListener` —— 少一层魔法。
- 客户端 mod 构造器可同时注入 `IEventBus` 和 `ModContainer`。

## M2 传播模型（已完成，待实机验证）

### 起因：用户发现 Q 值语义有缺陷

用户观察到"Q 值好像是根据对方客户端确定的"，问 3 台以上电台时怎么取值。
查代码确认是真缺陷：原实现 `best = max(quality(distance))` —— 只算"与最近那个人的链路"，
其余链路根本没算，靠两台电台的对称性蒙对了 HUD。

**结论：Q 本质是有向、成对的，不是信道属性。**
- 距离/遮挡每条链路不同
- 发射功率/天线（将来）导致方向性
- 接收者不同 → 同一句话降级不同
- 语音天然需要"每个远端说话人一个 Q"（SVC 空间音频按发声者处理）

### M2 做的改造

1. **Q 改成有向成对**：`Map<LinkKey(发射者UUID, 接收者UUID), Double> LINK_QUALITY`
2. **HUD 汇总值改为"最好链路 + 能听到几个台"**，不用平均值（3 人以上平均值会骗人）
3. **频段表** `RadioBands`（短波/中波/长波），各自 range / 衰减指数 / 占用损失倍率 /
   遮挡上限 / 天气敏感度。刻意做成"低频穿透强射程短，高频射程远怕遮挡怕天气"的取舍。
4. **DDA 体素遍历遮挡** `BlockOcclusion`（Amanatides–Woo，不是固定间距采样）
5. **天气损失**：路径中点判断 `isRainingAt`，雷暴 > 下雨
6. **tick 预算切片**：N² 条链路用线性游标走矩阵，超预算从断点返回，下周期接着算

### 合成公式

```
Q = pow(1 - d/range, exponent) × (1 - 遮挡比例) - 天气损失
```
距离与遮挡相乘（遮挡是路径累积削弱），天气相减（全局底噪恶化）。最后 clamp 0..1。

### 踩到的坑 / 关键判断

- **遮挡不能加载区块**：`level.isLoaded(pos)` 为假时按默认损失估算，绝不让射线触发世界生成。
- **花草火把不能算遮挡**：仅 `state.isAir()` 不够。规则改为
  覆盖表命中 → 用覆盖值；否则 `!state.canOcclude()` → 0（无碰撞方块不遮挡）。
  `canOcclude()` 是 BlockState 缓存的布尔值，不分配对象，可放热路径。
- 覆盖表用 `IdentityHashMap<Block, Double>`，避免每方块走一次注册表查找。
- 发射路径**不复用缓存**，重新算一次 —— 这句话必须按"此刻"的地形和天气送达。
- RadioBands 写死在代码里而不是 TOML：频段是一组相互关联的参数，拆开逐项配容易配出
  不合理组合。管理员用 rangeMultiplier 等倍率整体调。

## Bug 修复：界面读不到服务端刚同步的频率

现象：面板里按回车改频率后，右上角波段名不刷新，重开界面才正确。

**根因（重要，会再犯）：** `RadioScreen` 缓存了打开界面时的 `ItemStack` 引用。
服务端改完数据组件同步回来时，原版是把槽位里的 **ItemStack 整个替换掉**，
而不是原地修改 —— 所以缓存的引用变成"上一帧的旧对象"，读到的永远是旧频率。

**修复：** 不缓存 ItemStack，改为每次从玩家手上重新解析：

```java
private ItemStack radio() {
    Player p = Minecraft.getInstance().player;
    if (p != null) {
        ItemStack cur = HandheldRadioItem.findRadio(p);
        if (!cur.isEmpty()) return cur;
    }
    return initialRadio;  // 仅供兜底
}
```
界面打开期间玩家无法切换手持物，所以这个查询稳定且便宜。

**推论：任何需要长期持有的 ItemStack/BlockEntity 引用都要警惕这个模式。**
开机按钮标签是同一个 bug（走的是同一个缓存），一并对了。

## M3 与语音的排序讨论（我的建议，待用户确认）

M3 原定 = 表现层：调频 GUI（已完成）、信号指示（部分完成）、噪声音效、文本乱码（已完成）。
真正剩下的只有音效和 HUD。

### 建议 1：M3 的音效部分大幅缩减

理由：接语音后，噪声/低通/断音全部由 SVC 音频通道处理，现在用原版 SoundEvent 做的
噪声循环必然被整体替换 —— 调一套"听起来像无线电"的噪声是注定丢弃的工作。
只保留离散音效（开关机/发射/静噪）。

### 建议 2：M3 的核心产出是两件为语音铺路的东西

1. **`SignalEffects` 映射层**：Q → (可读度, 噪声底, 低通截止, 断音率)。
   文本消费前两项，音频将来消费全部。**这个不会因接语音而丢弃。**
2. **逐说话人 Q 协议**：现在 S2C 只有一个汇总值。语音需要"每个正在说话的人一个 Q"。
   纯协议工作，与 SVC 解耦，可以先用文本模式验证。

### 建议 3：语音提前到 M4，中继/固定台推后

- 把最不确定的放前面：SVC 客户端音频注入是唯一无法完全掌控的环节（版本敏感、
  可能要 mixin 进 AudioChannel 解码后播放前）。代码库还小时撞墙容易绕。
- 核心体验优先：中继/固定台/加密是玩法深度，语音是核心体验。

### 关键区分：语音 = 传输 + 表现，两件事难度差很多

| 部分 | 做什么 | 难度 | 依赖 |
|---|---|---|---|
| 传输 | 送真人声 | 高 | SVC / 自研 Opus 流 |
| 表现 | 按 Q 让音频像电台 | 中 | 我们自己 |

只做"听起来像电台"用原版 SoundEvent + Q 驱动失真就够，**不需要 SVC**。
必须用 SVC 的唯一理由是传真人语音。所以 M3 可独立完成并验证，不被 SVC 卡住。

### SVC 风险（动手前要先做可行性验证）

SVC 1.21.1 版本待确认；客户端自定义音频不是稳定 API，可能需要 mixin 注入。
备选（自研 Opus + 原版 SoundInstance）≈ 重写半个 SVC，工程量不可接受。

## M3 表现层（缩水版，已完成，待实机验证）

用户选择：M3 只做"可复用资产 + 最小音效"，SVC 硬/软依赖等可行性验证后再定。

### 产出

1. **`radio/SignalEffects`** —— Q → 感官参数，文本与语音的共同上游
   ```java
   record SignalEffects(double readability, double noiseFloor, double lowpassHz, double dropoutRate)
   ```
   - readability = clamp((q - unusable) / (clear - unusable))
   - lowpass 用**对数**插值（人耳感知是对数的，线性会让前半段没变化后半段突变）
   - dropout = (1 - readability) * maxDropoutRate
   - 新增配置节 `effects`：clearThreshold / unusableThreshold / lowpassMinHz /
     lowpassMaxHz / maxDropoutRate
2. **`TextDegrader` 重构**为 SignalEffects 的消费者，不再自己藏阈值。
   错字率 = (1-readability) * 0.62，掉字率 = dropout * 0.18。
3. **逐说话人 Q 协议** `S2CRadioState` 增加 `List<SpeakerLink(UUID speaker, float quality)>`
   - 语音的音频处理必须知道"正在说话的这个人是多少质量"，这个数只在服务端算得出
   - 提前定协议，语音接入时不用再动网络层和状态机
   - 链路列表参与变化判定，否则"人没变但地形变了"不会触发同步
4. **`radio/RadioSounds`** —— 全部复用原版音效，零资产：NOTE_BLOCK_BIT（开关机）、
   UI_BUTTON_CLICK（发射键、静噪）、NOTE_BLOCK_BASS（空频率）
5. **面板信号条**：20 格填充条，按 Q 分四档配色（青/黄/橙/红），PANEL_H 132→146

## SVC 调研结论（重要，决定 M4 走法）

### 许可证：All Rights Reserved，不能摘代码

```
Copyright (c) Max Henkel - All Rights Reserved
```
文件位置：仓库根目录 `license`（非 LICENSE，注意大小写）；Modrinth 也标注 "Licensed ARR"。

**源码可见 ≠ 开源。** ARR 下复制、修改、分发衍生作品全部禁止。
唯一合法用法：依赖它 + 通过它公开的 API 集成（作者明确发布 API 给 addon 用）。
→ 结论：**调接口，不摘代码。** 这既是法律要求，技术上也是对的（见下）。

### 技术理由（即使没有法律问题也不该摘）

- 摘了就永远跟不上上游。SVC 更新极频繁（2026-09-20 还在发 2.6.24 beta）。
- 我们需要的恰好是最难摘的部分：独立 UDP 端口（默认 24454）、NAT、AES-GCM、
  Opus 编解码、RNNoise 降噪、OpenAL 3D 音效、跨 Fabric/Neo/Forge/Paper/Quilt 兼容。
  摘得越多越是在重写 SVC。
- 我们真正要做的只是在**已解码的 PCM 上做 DSP**，这个位置 API 正好暴露了。

### API 里正好有需要的钩子（无需 mixin）

`api/src/main/java/de/maxhenkel/voicechat/api/events/` 共 40 个事件类，关键的有：

| 事件 | 侧 | 用途 |
|---|---|---|
| `ClientReceiveSoundEvent` | 客户端 | 收到声音时触发 = "解码后、播放前"，DSP 的落点 |
| `ClientSoundEvent` / `MergeClientSoundEvent` | 客户端 | 修改/合并客户端声音 |
| `OpenALSoundEvent` / `CreateOpenALContextEvent` | 客户端 | 更底层 |
| `VoiceDistanceEvent` | 服务端 | 自定义距离逻辑（官方 changelog 明示支持） |
| `MicrophonePacketEvent` | 服务端 | 拦截麦克风包 |
| `PlayerStateChangedEvent` | 服务端 | 谁在说话 |

包结构还有 `audio` / `audiochannel` / `audiolistener` / `audiosender` / `opus` / `mp3` /
`packets` / `config`，以及 `Player` / `Group` / `Entity` / `Position`。

### 最关键的设计发现：两个钩子分管两件事

SVC 默认是距离语音，超过 `voice_chat_distance` **完全收不到包**。
而无线电是"越远越差但不会消失"。所以必须拆开：

- **能不能收到包** → `VoiceDistanceEvent`（同频且有电台：拉满距离；没电台：0）
- **收到后有多清楚** → `ClientReceiveSoundEvent` + 既有 `SignalEffects`

否则 300 格外的队友在 SVC 层面根本没声音包，DSP 没机会处理。

**副作用（正向）**：这顺带解锁邻频干扰玩法 —— 同频/邻频的人都收得到包，
由 DSP 决定"听清 / 听不清 / 全是噪声"，比让 SVC 直接静音更符合硬核无线电。

**副作用（需处理）**：装了本 mod 后 SVC 不再是纯距离语音，这是侵入性玩法改变。
必须做成可关闭：只有"手持开机电台"的玩家走无线电逻辑，其他玩家保持 SVC 原版行为。

## M4 语音实装（已完成，待实机验证）

### spike 日志给出的两个关键事实

```
VoiceDistanceEvent      → [VoiceChatPacketProcessingThread]
ClientReceiveSoundEvent → [AudioChannelThread-<channelUUID>]
```

1. **两个钩子都不在主线程**。前者在 SVC 的包处理线程，后者**每个音频通道一个线程**
   （通道 UUID = 说话人实体 UUID）。所以：逐说话人的 DSP 状态天然免锁，
   但回调里绝不能碰世界或可变集合，只能读不可变快照。
2. **`getDistance()` 返回 48.00 而不是真实距离** —— 它是 SVC 的配置值，对我们没用。
   幸好 Q 一直是服务端算的。
3. `采样数=960` → **48000Hz / 16bit / 单声道 / 20ms 一帧**。峰值静音帧 1~2、
   说话帧 6999，16bit 量程正常。
4. SVC 本体自带 `voicechat_api` **2.6.20**，和我们 compileOnly 的版本完全一致
   （日志：`{voicechat,voicechat_api} ... {1.21.1-2.6.22, 2.6.20}`）——版本配对确认无误。

### 实现

**服务端（`OpenRadioVoicePlugin.onVoiceDistance`）**：只扩大、不缩小。
有开机电台的人，把广播半径撑到该频段射程（`min(band.maxRange * multiplier, maxBroadcastRadius)`）。
不这么做的话 SVC 默认 48 格，300 格外的队友连包都收不到。
缩小范围没意义（接收端查不到 Q 就静音），而且在传输层设 0 之类的激进值可能踩边界行为。

**线程安全**：主线程每个传播周期构造不可变 `VoiceSnapshot(Map<UUID, Float>)`，
整体替换 `volatile` 引用。SVC 线程只读，无需加锁。见 `radio/VoiceSnapshot`。

**客户端（`onEntitySound`）**：
```java
float q = ClientRadioState.qualityFrom(event.getEntityId());
if (q <= 0) → 全零帧（不在链路上）
else       → RadioVoiceProcessor.process(audio, SignalEffects.of(q), stateFor(uuid))
```
`links` 里只包含"同频 + 有开机电台"的人，所以查不到 = 静音 = **完全替代 SVC 真正生效的地方**。

**DSP 链**（`voice/RadioVoiceProcessor`）：
```
高通(300Hz) → 低通(Q 决定) → 信号中断门 → 音量 → 叠加白噪声
```
- 高通放最前：这才是"像不像电台"的决定因素，只加噪声只是"加了噪的语音"
- **中断时保留噪声**：真实无线电信号衰落时听到的是更响的噪声，不是安静。
  所以门只掐人声，噪声在门之后叠加
- 门有 48 采样（1ms）斜坡，硬切会产生宽带冲击听成"咔"
- 每帧（20ms）决定一次是否中断，而不是逐采样 —— 逐采样听起来像嗡嗡失真，
  逐帧才像信号断续。系数 0.6 让曲线偏向"偶有断续"而非抽搐
- 每次 `setRawAudio` 用**新数组**，不原地改，避免和 SVC 共用缓冲区出问题

**状态**：`VoiceChannelState` 跨帧保留滤波器记忆（每帧重建 = 没滤波 + 爆音）。
`ConcurrentHashMap` 上限 64，超了整体 clear（滤波器重置无害）。

**噪声曲线**：`noiseFloor = pow(1-Q, 1.6)`。线性曲线高档位噪声太多、低档位不够凶。

`voice.noiseGain`(0.30) / `voice.highpassHz`(300) / `voice.minVoiceGain`(0.55) /
`voice.maxBroadcastRadius`(4096)。原有 `enabled` / `replaceVanillaBehavior` /
`debugSilenceAllVoice`（默认已改 false）。

## M4.1 远距离语音失效 —— SVC 的实体制约（重要）

现象：1500 格时文字能收到、UI 显示链路正常，**语音完全没声音**。近距离正常。

根因**不是** `max_voice_distance`/广播半径（那个早就用 `VoiceDistanceEvent` 撑到 2048 了），
而是 SVC 客户端 `AudioChannel` 对 `PlayerSoundPacket` 的处理：

```
level.getPlayerByUUID(sender) → null → 在 AABB(±distance) 里再找一遍 → 仍是 null → return
```

实体只在视距内被跟踪（原版玩家实体跟踪上限 32 区块，实际受视距约束），
所以超过一百多格，听众客户端上根本不存在说话者实体，SVC 直接丢掉这一帧，
**连 `ClientReceiveSoundEvent` 都不会触发**。这是 SVC 的设计，绕不过去。

### 解法：服务端转发静态音频

`MicrophonePacketEvent`（可取消，`PluginManager.onMicPacket` 返回 isCancelled 并跳过
`processMicPacket`）里拿到原始 Opus 帧：

```java
StaticSoundPacket packet = event.getPacket().toStaticSoundPacket();   // channelId = 说话者 UUID
for (UUID listener : routes) serverApi.sendStaticSoundPacketTo(conn, packet);
event.cancel();   // 必须取消，否则近处会听到原版 + 转发两份叠加
```

静态包在客户端走 `GroupSoundPacket` 分支：**不查实体**、非定位、全音量播放，
并回调 `ClientReceiveSoundEvent.StaticSound`，`getId()` 正好是说话者 UUID → 查 Q 用。

实现落点：
- `radio/VoiceSnapshot` 增加 `routesBySpeaker: Map<说话者, Map<听众, Q>>`，
  主线程每传播周期重建并整体替换引用（SVC 线程只读）。
- `voice/OpenRadioVoicePlugin` 只管服务端（VoiceDistance 兜底 + 麦克风包转发）。
- `client/VoiceClientHandlers` 单独成类装音频处理 —— 专用服务器没有
  `net.minecraft.client.*`，混在插件类里会 NoClassDefFoundError。
- 静态包是所有 addon 共用的通道，所以用 tab 列表（`getOnlinePlayers()`）判定
  "这个 channelId 是不是本服玩家"，不是就原样放过，避免把别人的音频静音。

排查顺序：服务端日志 `[voice] 转发一帧语音给 N 人`。
N=0 → 链路表空（频率不同/超射程/没开机）；N>0 但听不到 → 问题在客户端接收侧。
