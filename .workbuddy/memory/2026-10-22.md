## 关键新发现（改变了之前的结论）

翻 `voicechat-api-2.6.20.jar` 发现 SVC 公开了**主动推送音频**的能力：

```
VoicechatServerApi.createStaticAudioChannel(UUID)
StaticAudioChannel.addTarget(VoicechatConnection)
VoicechatServerApi.createAudioPlayer(AudioChannel, OpusEncoder, Supplier<short[]>)
VoicechatApi.createEncoder(OpusEncoderMode)
api/opus/OpusEncoder { byte[] encode(short[]); }
api/audio/AudioConverter { short[] bytesToShorts(byte[]); ... }
```

所以 SSTV 可以走**真实音频**而不是数据分块 —— 图像质量会自然跟随传播模型
（低 Q → 噪声/低通/断音 → 解调失败 → 逐行撕裂），不需要写任何额外降级逻辑。
这是原"绝不走语音通道"结论的修正原因：之前只查了 `ClientReceiveSoundEvent`，
没查 encoder/audio channel 这一侧。

**M6 开工第一件事（必须验证）**：静态音频通道的包在客户端是否触发
`ClientReceiveSoundEvent.StaticSound`；`getId()` 返回通道 UUID 还是玩家 UUID。
若是通道 UUID，`VoiceSnapshot` 要加 `通道UUID → 发送者` 映射。

## M5 实现（已完成代码 + 加载验证）

### 电池：物品，但没有槽位

用户方案：**电台放副手、主手持电池右键更换**。实现后确认这个方案比"消耗品充电"更好：
- `ModDataComponents.BATTERY` = `DataComponentType<ItemStack>`（`ItemStack.OPTIONAL_CODEC`，
  空电池必须能序列化）。电池能量在 `ENERGY` int 组件上。
- 右键优先级：**换电池 > 潜行拆电池 > 开关机**。顺序反了会导致"拿电池右键变成开机"。
- 仍然没有 `Menu`，所以 M5 最大的复制漏洞面不存在。但**组件里的嵌套 ItemStack 必须
  copy 后再改**：组件是不可变共享对象，原地改会让所有持有同一组件的栈同时变化。

### 能量（FE）

- `energy/ModCapabilities`：`Capabilities.EnergyStorage.ITEM`（**不是 `Capability`，
  1.21.1 里没有这个类**），电池可充可放；电台是代理、`canExtract=false`。
- 语音耗电走 `energy/VoicePowerLedger`：SVC 包线程只累加整数账，主线程每周期 `take()`。
- **按帧直接扣会永远是 0**（40 FE/s ÷ 50 帧 = 0.8）。必须数满 50 帧记一次整数。
- 待机耗电需要小数余额（60 FE/min ÷ 1200 tick × 10 = 0.5），用 `IDLE_RESIDUAL` 累计。

### 天线

- `AntennaKind` 枚举 + `AntennaProvider` 接口 + `Antennas.resolve`（手持→护甲）。
  背包/胸甲以后实现同一个接口即可，传播计算不用动。
- 射程 = `band.maxRange × rangeMultiplier × √(发送端系数 × 接收端系数)`。
  用几何平均，直接相乘会失控（1.6² = 2.56）。
- 装错波段 = 0.8 倍（不是 0），UI 明确写"不匹配（当前长波）"。

### 静噪

- `SQUELCH` float 组件 + `C2SSetSquelch` 包（要持久化到物品，所以必须过服务端）。
- **只作用于语音**，不拦文本 —— 文本是数据模式，静噪是音频门。
- 客户端缓存在 `ClientRadioState.squelch`，音频线程只读这个 float，不碰背包。
- 逐说话人判定：邻居很响不代表远处那台能挤进来。

## 崩溃修复：数据组件不能存 ItemStack（重要）

**症状**：进存档后按 E 打开物品栏，游戏立刻崩溃。

```
IllegalArgumentException: Data components must implement equals and hashCode.
Problematic class: class net.minecraft.world.item.ItemStack
  at RadioEnergy.setBattery   → ModCreativeTabs.lambda
  at CreativeModeTabs.buildAllTabContents
```

**根因**：`ItemStack.set()` 里 NeoForge 会调 `CommonHooks.validateComponent`，
要求组件值**不可变且实现 equals/hashCode**。`ItemStack` 恰好没有 equals（用身份比较），
所以「把电池物品塞进电台的 DataComponent」这条路在 NeoForge 上根本不成立 ——
不只是创造页，装电池时一样会崩。

**修法**：电池不再以 ItemStack 形式存在电台里，改成两个组件：
- `battery_present`（boolean）：装没装电池
- `energy`（int）：那块电池还剩多少 FE

换电池 = 把电台里的 `energy` 取出来、重新构造一个电池物品还给玩家；
装电池 = 把手上电池的 `energy` 写进电台。语义完全不变，同步数据还更少。
`RadioEnergy` 的 API 相应改成 `install(radio, energy) / eject(radio) → 剩余电量`。

**教训（写进 MEMORY.md）**：DataComponent 只能存**原始类型、record、或实现了 equals 的不可变类**。
要存物品请用 `battery_present + 数值` 这种拆解方式，不要存 ItemStack。

**副作用**：旧存档里的电台带着已经不存在的 `battery` 组件，会被忽略，
表现为"没有电池"，需要重新装一块。0.x 阶段可以接受。

**验证**：`gradlew build` 通过；`runClient` 加载 0 ERROR、
`Data components must implement` 出现 0 次；创造页是否还会崩需要用户按 E 实测。

## 修复：每次扣电触发"重新装备"动画

**症状**：电台开机后，每次扣电（待机每传播周期、发射、语音结算）第一人称视角里
物品都会下沉再抬起一次，像反复重新掏出电台。

**根因**：NeoForge `IItemExtension#shouldCauseReequipAnimation` 默认实现是
`!oldStack.equals(newStack)`，而 `ItemStack.equals` 比较**完整组件集合**。
电台的电量/频率/开关机都存组件，任何一次变化都被判定成"换了物品" →
`ItemInHandRenderer.tick()` 里 `requipM = true` → `mainHandHeight` 被拉回 0 → 播动画。
（`tick()` 用的是 `ClientHooks.shouldCauseReequipAnimation(old, new, slot)`，
玩家切槽位时 `slot != slotMainHand` 也会触发，那条逻辑要保留。）

**修法**：在 `HandheldRadioItem` 覆写

```java
public boolean shouldCauseReequipAnimation(ItemStack oldStack, ItemStack newStack, boolean slotChanged) {
    return slotChanged || !ItemStack.isSameItem(oldStack, newStack);
}
```

`isSameItem` 只比较 item 本身、忽略组件。同一台电台的状态变化不再动画，
换手/切槽/换成电池照旧有动画。电台是 `stacksTo(1)`，所以忽略数量是安全的。

**验证**：`gradlew build` 通过；`runClient` 12:20:35 新一次启动
`OpenRadio initialised` + `client loaded`，0 ERROR。动画效果需实机观察。

**通用教训**：任何"状态频繁变化且存在组件里"的物品（电量、耐久替代、计时器）
都会踩这个坑。凡是这类物品都要覆写 `shouldCauseReequipAnimation`，
否则会持续播放装备动画。

## M6 前置验证通过：SVC 音频推送 + Opus 实测（重要）

### 链路：已确认可用

`createStaticAudioChannel` + `AudioPlayer` + `createEncoder` 这条"服务端自己生成音频推给玩家"
的路**实测通了**：2.2 秒 / 110 帧，客户端**零丢帧**收到，`StaticSound#getId()` 返回的是
**我们传入的通道 UUID**（不是玩家 UUID）。

反编译确认的三个关键行为：
- `AudioPlayerImpl` 是独立线程，用 `startNano + 帧序号 × 20ms` 排帧，**不累积漂移**
- 取帧返回 `null` = 结束；**帧长必须正好 960**，否则报错并停止（末帧必须补零）
- `StaticAudioChannelImpl.broadcast` 只遍历自己的 `targets`，所以 `addTarget` 全在
  `startPlaying()` 之前做完就没有跨线程问题
- `setOnStopped(encoder::close)` 必须加，否则每次发射漏一个 native 句柄

### 实测结论：我之前的判断是错的

**"VOIP 模式会削掉 1.5–2.3kHz" 是错的。** 实测（1000/1200/1500/1900/2300/2800Hz 六个频点
+ 1500→2300 线性扫频）：

| 模式 | 各频点衰减 | 扫频主频偏差 | 静音段噪声底 |
|---|---|---|---|
| AUDIO | ≤ 0.1dB | ≤ 20Hz（测量精度） | −270 dBFS |
| VOIP | ≤ 0.1dB | ≤ 20Hz | −112 dBFS |

原因：Opus 的 `application` 参数只影响 VAD/FEC/预滤波，**不改变带宽上限**；
削 1.5–2.3kHz 是 8kHz 窄带电话的行为，不是 Opus VOIP 模式。SVC 两种模式的
采样率/声道/比特率完全相同，只差一个 `Application` 枚举。
**仍选 AUDIO，但理由换成"关掉 VAD/DTX，行为可预测"。**

### 真正的约束是我们自己的 DSP，不是 Opus

按当前 `SignalEffects` 曲线算（一阶 RC 低通 + 20ms 帧门控）：

| Q | 低通 | 2300Hz 衰减 | 静音帧率 |
|---|---|---|---|
| 0.70 | 4628 | −1.0dB | 8% |
| 0.60 | 2678 | −2.4dB | 16% |
| 0.50 | 1549 | −5.1dB | 24% |
| 0.40 | 896 | −8.8dB | 32% |

低通不致命，**静音帧率致命**：SSTV 一行 ≈ 114ms ≈ 5.7 帧，Q=0.5 时平均每行丢 1.4 帧，
行同步必崩。所以 **M6 数字模式必须独立曲线：dropout=0、低通下限 ≥2600Hz、噪声保留**。
`SignalEffects` 的结构可复用，曲线要分模式。
